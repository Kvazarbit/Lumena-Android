# Когнітивний екзоскелет: двобічний досвід v1

## Межі реалізації

Це розширення наявної локальної контекстної ОС Lumena. Воно використовує
CoordinatorExperienceStore, ConstitutionGenome і ReflexKernel, а не створює
паралельний агент. Запит власника від 2026-09-26 розширює обсяг підготовки змін;
критерії готовності релізу з COMPLETION_PLAN залишаються чинними.

## Реальний цикл

1. Local і Companion записують результат інструмента в приватний AtomicFile.
2. Після невдачі оцінюється **наступна** спроба того самого інструмента над тим
   самим об'єктом, максимум шість кроків. Пізніший успіх не приховує провалені спроби.
3. Успіх утворює RECOVERY; невдача — FAILED_RECOVERY. Усі кроки мають посилання
   на докази. Невідомий результат є бар'єром: через нього не створюється навчальний приклад.
4. Для Local і Companion добір прикладів відфільтровано за проєктом/глобальною
   областю й ідентифікатором моделі **до** top-k. Нерозмічені старі приклади
   лишаються в сховищі, але не переносяться автоматично в нову область порад.
5. Reflex враховує максимум один голос задачі для кожного варіанта відновлення.
   Якщо задача містила і провал, і успіх такого варіанта, голос консервативно негативний.
   Негативні приклади знижують силу рекомендації; самі по собі не дозволяють нової дії.
6. Конституційний шаблон отримує AFFIRM або REJECT із локальними доказами.
   Суперечність переводить правило в CONTESTED і прибирає його з активних рекомендацій.
   Історія та походження зберігаються; перегляд/заміна можливі через наявний механізм
   supersedeAdvisory. Автоматичного оголошення суперечності вирішеною немає.
7. Реальні негативні епізоди з повною трасою утворюють обмежений корпус
   CognitiveRegressionSuite. Відтворення перевіряє збереження негативного досвіду
   після ущільнення журналу. Diagnostics додає [COGNITIVE_EXPERIENCE].

## Що вимірюється

- failedAttemptIsRetainedEvenWhenLaterAttemptRecovers: без упередження виживання;
- missingIntermediateEvidenceCannotBecomeVerifiedRecovery: повнота доказів;
- repeatedExamplesFromOneTaskCannotPretendToBeIndependentExperience: захист від повторного підрахунку;
- CognitiveExperienceFeedbackTest: негативний зворотний зв'язок, суперечності правил,
  невідомі результати, ізоляція, JSON-перезапуск, регресії для пошуку/коду/читання.

До виправлення три перші тести падають на твердженнях на SHA 21ace87.
На локальному JVM-прогоні після змін проходять 60 тестів відповідних політик.
Вивід: `evidence/cognitive-experience/baseline-jvm.txt` і `updated-jvm.txt`.
Повтор у штатному середовищі: `gradle testDebugUnitTest` (повний набір).
Компілятор локального прогону: Kotlin 1.9.23 / JDK 17; Android API 35 використано
лише для компіляції інтерфейсів Context/AtomicFile. Android I/O та Compose цим
прогоном не перевірялись. Повний Android CI використовує проєктний Kotlin 2.0.21.

Корпус — регресійний тест пам'яті й керування. Це **не** доказ інтелекту моделі,
успіху довільної мети, переваги над іншими агентами чи причинності стратегії.
0 cases означає відсутність даних. Лічильники в Diagnostics не є точністю моделі.
Функція holdout задає стабільний поділ за всією вихідною задачею для майбутніх
контрольованих експериментів; автоматичне A/B-вимірювання якості LLM тут не реалізоване.

## Сумісність і відкочування

Нові поля мають значення за замовчуванням; JSON v2 читається. Події зберігаються
в наявному обмеженому журналі (2048), приклади — у наявному playbook (512).
Експорт/імпорт зберігає FAILED_RECOVERY як контрприклад, не як успішний рецепт;
імпортовані дані залишаються доказами іншого пристрою й потребують локальної перевірки.
Старий APK, який не знає нового enum, може відхилити оновлену пам'ять. Для повернення
до старого APK потрібен сумісний експорт/знімок до оновлення; дані автоматично не видаляються.
Новий приватний ключ підпису та міграція встановленого APK не входять у цю зміну.

## Наступні вимірювані межі

- перевірка актуальності після зміни backend/пристрою/конфігурації понад modelId;
- класифікація причин невдач для точнішого перенесення стратегій;
- незалежні оцінювачі цілей для дослідження й програмування;
- контрольований A/B-прогін із замороженою навчальною пам'яттю та невиданими задачами;
- phone smoke, release-підпис і відсутні захисти #89/#91 за планом стабілізації.

Навчені правила не змінюють ToolGate, дозволи, бюджети або критерії done.
Нові вільнотекстові «геніальні ідеї» не встановлюються як виконуваний код без перевірки.
