# Перевірюваний контур досвіду — робочий етап

Дата: 2026-10-19. Гілка: `codex/verified-experience-loop`.
База: успішний Daily Context OS `c5120f35` і ClaimCheck Опуса `96c8e820`.
Збірки Опуса 2328/2329 завершилися успішно до початку інтеграції.
Настільний `back_003` залишається лише джерелом прикладів, без змін і запуску.

## Межі доказу та вимірювання

Випадок — спостережений зв'язок виправлення з незмінною перевіркою. Він не доводить
єдину причину і не робить тестову систему повною специфікацією мети. Межу tests/helpers/
fixtures визначає власник. Обмежене хешування позначає неповне покриття; воно не
маскується під повну перевірку. Bridge не є OS-пісочницею: процес під тим самим UID
може тимчасово змінити й відновити файли всередині запуску. Для ворожого коду потрібен
окремий захищений verifier. Новий доказ не видається для legacy-квитанцій.

Дослід вимірює допомогу кейсів за наявних однакових захисних механізмів. Показ кейсів
дозволений у явному лабораторному режимі до доведення користі; це виняток до правила
про непідтверджені похідні поради, не вимкнення конституції. Бібліотека фіксується
до рандомізації, нові кейси не підмішуються в поточний дослід. Модель не переходить
між плечима після кожної невдалої спроби.

80–84 епізоди — умовний розрахунок для великого ефекту та незалежних спостережень.
20 багів × 4 повторення не дорівнюють 80 незалежним проблемам. Для lab потрібні
окремі навчальні/контрольні задачі, свіжі копії робочих каталогів та незмінний acceptance
поза інструментальним простором моделі. Звіт показує числа й обмеження, не обіцяє виграш
за кілька вечорів. Старий LayerGovernor рандомізує доступні шари незалежно; він не
розбиває всі задачі на 8 непересічних груп.

Кейси лишаються в межах проєкту. Навіть короткі повідомлення помилок можуть містити
секрети; автоматичного перенесення «уроків» між проєктами немає. Зовнішня передача
підкоряється чинним дозволам власника. Архівні факти не стають поточним PASS і не
переносять право запуску інструментів.

## Журнал виконання

- План погоджено користувачем. Інтеграція Опуса завершена в окремій гілці.
- A–E реалізовані; 110 локальних Python-тестів пройшли, включно зі справжнім pytest FAIL → правка → PASS. Чотири Bash-тести встановлювача перевіряються в Linux CI.
- F: повний Android CI й Kotlin/Robolectric перевірки очікуються. Фізичне приймання NOT_RUN.
- CI #2330: 113 із 114 Linux Python-тестів пройшли; справжній pytest не побачив user-site після ізоляції HOME. Для наступної ревізії CI отримав окремий Python 3.11. Цільовий Kotlin/Robolectric baseline цієї ревізії пройшов; семантичні перевірки ще тривають.

## Як користуватися цим етапом

1. Оновити APK тим самим ключем, без видалення застосунку. Оновити bridge до 0.33:
   health має містити `verification_boundary_v1` та `file_cas_v1`.
2. Відкрити Проєкти, обрати каталог і мету, ввімкнути локальний журнал. У «Досвід
   проєкту й лабораторія» вказати `tests` та всі helpers/fixtures, які визначають приймання.
   Порожній список зберігає звичайну роботу, але не створює кейсів. Зміна списку
   змінює версію мети; старий pending-запуск під новою метою не виконується.
3. Виконувати звичайні задачі. Природний ланцюжок FAIL → файл → PASS у межах одного
   зобов'язання створить кейс. Для продовження користуватися кнопкою «Продовжити».
   Змінений тест, пропущений тест, UNKNOWN або довільний `python.run` усередині
   ланцюжка не створюють кейсу. Ліміт епізоду — 8 наступних квитанцій інструментів.
   Невирішений/неповний інтервал не починає нового призначення на кожному FAIL:
   спершу потрібен справжній PASS. Результати призначених епізодів читаються з повної
   історії, навіть коли вони випали з останніх 256 звичайних записів огляду.
4. Для досліду потрібен хоча б один кейс, локальна Ollama з підтвердженим маршрутом
   та її справжній digest з `/api/tags`. Вбудована модель працює звичайно; лабораторна
   атестація її ваг ще не реалізована. Це обмеження виміру, не вимога замінити модель.
5. «Почати дослід 50/50» фіксує бібліотеку, модель, застосунок і пристрій. Повтори
   зберігають плече. Зміна умов зупиняє дослід; відомі призначення зберігаються у звіті.
   Звіт описовий: SOLVED/UNRESOLVED/відкриті, медіана кроків лише розв'язаних,
   прийняті й відхилені розпізнані DONE. Відхилений DONE залишає зобов'язання відкритим.
   Окремо рахуються підготовлені запити та наявність кейсу в них; це не доказ уваги моделі.
   Якщо текст кейсу потрапив у контроль із попередньої історії, призначення зберігається
   як змінені умови. Приклади можуть витісняти частину похідних порад у межах того самого
   бюджету; обов'язкові мета, обмеження та картка чинних квитанцій зберігають пріоритет.
6. Копія всіх проєктів включає квитанції, workspace, історію, метадані дослідів та
   SHA-256 кожного файла. Це перевірка цілісності, не цифровий підпис автора архіву.
   Ліміти імпорту: 512 MiB, 400 файлів, 8 верхніх архівів; при переповненні дані не стираються.
7. Після перевстановлення кнопка «Відновлення з копії ZIP» доступна без створення
   проєкту. Спершу перевірити склад, потім відновити історію. Поточні проєкти не
   перезаписуються. Ключі, ваги моделей, файли робочого каталогу, права й незавершені
   команди ZIP не відновлює. Для старих ZIP без `integrity.json` перевіряється SQLite
   chain та workspace; невикористані байти SQLite не мають повної атестації.
8. Архівний UNKNOWN лишається UNKNOWN. Читання дозволено; після огляду реальних
   файлів власник окремо підтверджує наслідки в панелі архівів. Поточні живі UNKNOWN
   мають власний чинний бар'єр і цим підтвердженням не знімаються.

У цьому етапі архівні квитанції показані як історія в панелі архівів; автоматично
в картку поточних доказів або лабораторну бібліотеку вони не додаються. Історію
дослідів експортовано для аналізу; імпорт не відновлює активний дослід. Нових
неперевірених проєктних Fractal-порад у контексті немає; наявні записи збережено.
Журнал та обов'язкові рішення/обмеження власника продовжують працювати.
