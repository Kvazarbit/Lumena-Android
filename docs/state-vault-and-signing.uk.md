# Стан поза APK та сумісні оновлення

## Ключ

ci1383 і ci1385 мають різні debug-сертифікати; оновлення між ними неможливе.
v0.12.7 переходить на постійний приватний ключ власника. Публічний відбиток
закріплено в signing/certificate.sha256. Приватного ключа в git немає.

У GitHub Settings → Secrets and variables → Actions створити `LUMENA_SIGNING_BUNDLE`:
значення — повний JSON із приватного резервного пакета власника. Script sign_apk.py
перевіряє сертифікат до підпису та після підпису. Несумісний ключ не приймається.
Без секрету CI створює тільки явно позначений UNSIGNED signing-input, а не інший debug APK.
Для першої збірки допустимий локальний підпис тим самим ключем та тим самим скриптом.
Усі подальші оновлення потребують збереження ключа, package ID і зростання versionCode.
Одноразове видалення старого несумісного APK виконує власник після збереження потрібних даних.

### Локальна копія ключа для підпису в Termux

`scripts/sign_lumena.py` підписує з зашифрованого пакета `~/.lumena/Lumena-signing.enc`.
Пароль-фразу він питає в терміналі через getpass щоразу. Відкритий
`Lumena-private-signing-backup.zip` відхиляється. Працювати з ним можна лише з явним
`--allow-plaintext-backup`, і тоді скрипт друкує гучне попередження.
Шифрування робиться один раз командою `python sign_lumena.py --encrypt-backup`:
фраза вводиться двічі (щонайменше 12 символів), файл перечитується й перевіряється.
Відкритий ZIP скрипт сам не видаляє. Його прибирає окрема команда
`python sign_lumena.py --encrypt-backup --delete-plaintext`: вона ще раз питає фразу
і видаляє ZIP лише тоді, коли пакет відкривається й містить саме цей ZIP.
Перед видаленням скопіюйте `.enc` в друге безпечне місце. Без фрази або без файла
оновлення Lumena «поверх» стане неможливим.

Формат використовує лише стандартну бібліотеку Python: scrypt (N=2^17, r=8, p=1,
випадкова сіль) дає окремі ключі шифрування й MAC. Потік шифру — HMAC-SHA256 у режимі
лічильника з випадковим nonce. Тег HMAC-SHA256 покриває заголовок і шифротекст
(encrypt-then-MAC). Це підручникова конструкція, а не перевірений AEAD, і незалежного
аудиту вона не мала. Подробиці в `docs/OWNER_SIGNING.md`.
Шифрування захищає копію «у спокої»: інструменти bridge, копії, бекапи бачать лише шифротекст.
Воно не захищає від процесу того самого користувача Termux під час підпису.

## Папка

Tools → Папка пам’яті Lumena → Вибрати папку збереження. Рекомендовано окрему папку
Documents/Lumena. Android не дозволяє вибирати деякі кореневі/захищені папки.
Доступ надається через системний picker, без доступу до всього накопичувача.

Робочі сховища залишаються приватними. Обрана папка містить ZIP-копії `.lumena.zip`:
- історія гілок, поточна сесія і чернетка Companion;
- позитивний/негативний досвід, coordinator events, конституція;
- Context Genome / ландшафт досвіду (SQLite), Evidence Graph;
- калібрування, Laya shadow, стан web research та переносне ядро;
- модель/обчислювальні налаштування без облікових даних.

Не включаються APK, моделі GGUF, проєкти Termux, bridge token, доступи SAF,
дозволи виконання та активний checkpoint агента. Це копія збереженого стану,
а не всі давні повідомлення поза вже наявними лімітами історії.
Архіви містять приватні чати у відкритому вигляді: обирайте приватну папку.

Автозбереження запитується після сесії/Companion outcome та перевіряється раз на 30 с,
поки процес працює. Воно не є гарантією роботи після Android force-stop/знищення процесу.
Без змін нова копія не створюється. Зберігаються останні 10 іменованих копій;
попередні видаляються лише після успішного запису/повторного читання нової.
Перед видаленням APK: «Зберегти зараз», перевірити статус і бажано скопіювати архів
на інший носій. Недоступна папка/відкликаний доступ дають помилку, не фальшивий успіх.

## Відновлення

«Завантажити з папки…» показує доступні копії. Після явного підтвердження заміни
архів перевіряється, staging зберігається приватно; інші агентські дії блокуються.
Закрити застосунок кнопкою та відкрити знову. Application.onCreate виконує restore
до ініціалізації Activity/service/store, з локальним журналом відкату.
Після збою застосування наступний запуск повертає попередній стан до відкриття UI.
При помилці відкату звичайний UI не запускається, журнал зберігається.

ZIP має точний allowlist назв, межу 64 МБ, версію, SHA-256 кожного файла та
перевірку SQLite integrity_check. Пошкоджені/неповні/новіші архіви відхиляються.
Хеші захищають від пошкодження, не доводять довіру до автора: відновлюйте лише власні копії.
Незавершені task/pending у сесії та гілках скасовуються; Safe Auto і auto-return
після restore вимикаються. Поточний bridge token не замінюється з архіву.

Після перевстановлення доступ до папки треба надати знову. Відновлення з папки
не змінює папку автозбереження: її слід обрати окремо, щоб випадково не писати у джерело.
Телефонна перевірка Android picker/SQLite/жестів і install-update залишається окремим кроком.
