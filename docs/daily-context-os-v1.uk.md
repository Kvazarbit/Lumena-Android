# Щоденна робота над проєктом — ОС контексту V1

Дата: 2026-10-19. База: `6c7a8ac3`. Робоча гілка: `codex/daily-context-os-v1`.

Мета: власник продовжує проєкт після закриття застосунку або зміни моделі,
зберігаючи мету, причини рішень, відкриті зобов'язання та справжні результати.
Настільний `back_003` — лише джерело прикладів, жодних змін або запусків його коду.

## Дерево реалізації й приймання

```text
V1
├─ S1. Достовірність
│  ├─ Мета / охоплені джерела / збірка — окремі осі актуальності
│  ├─ Обмежений inventory не засвідчує весь проєкт
│  ├─ Git-зміни мають durable side effects навіть за незмінних source bytes
│  └─ Квитанція зберігає фактичні аргументи; сторонній шлях не переприписується
├─ S2. Межа приватності
│  ├─ Проєктний контекст за замовчуванням локальний
│  ├─ Приватна історія та її похідні не переходять на зовнішній маршрут
│  ├─ Власник явно дозволяє передачу контексту проєкту
│  └─ Перевірка перед model request охоплює restored/pending history
├─ S3. Картка продовження
│  ├─ Активне зобов'язання, причина рішення, відхилені альтернативи
│  ├─ Незавершені ефекти та наступна перевірка
│  ├─ Оновлення після інструментів, а не лише на початку задачі
│  └─ Вивантаження embedding-рушія не стирає проєкт
├─ S4. Збереження і відновлення
│  ├─ Сумісне читання старого стану без підвищення його довіри
│  ├─ Перервана дія відновлюється як UNKNOWN, без повторного transport
│  ├─ Архів завершених сегментів журналу з перевіреним ланцюжком
│  └─ Перерваний archive commit, нестача місця, tampering → збереження даних
├─ S5. Поведінкові перевірки
│  ├─ test → patch → той самий test; зміна мети за того самого вмісту
│  ├─ restart / інша модель / інший проєкт / private canary
│  ├─ unknown git outcome / новий файл / зовнішня зміна
│  └─ known-good + семантичні мутації з конкретною причиною відмови
└─ S6. Випуск
   ├─ Python bridge тести + Kotlin JVM/діагностичні тести у GitHub CI
   ├─ Прив'язка звітів і APK до одного commit
   └─ Підпис власним ключем та фізичне приймання на телефоні
```

## Порядок роботи

1. Для кожного механізму спочатку визначити спостережуваний сценарій і тест.
   Червоний тест повинен падати через конкретну відсутню поведінку; compile/setup
   errors не є підтвердженням. Після реалізації перевірити успішний контроль.
2. Реалізувати S1–S2 перед автоматичною передачею нової пам'яті моделям.
3. S3 використовує чинні ProjectWorkspace, ContextKernel і collaboration ledger.
   Нового конкуруючого сховища мети та окремої «конституції» не вводити.
4. S4 зберігає історичні факти й delivery identity. Архів не створює нового
   app-observed походження при імпорті. До transport резервується місце результату.
5. Запустити цільові тести, потім штатний CI. Будь-який збій виправити й повторити
   відповідний контроль. Повторні прогони без нової причини не потрібні.

## Продуктова поведінка

- Проєкти → обраний проєкт → Продовжити. Відкрита задача передається новому
  execution epoch зі збереженням походження попередніх результатів.
- Важливі рішення власника містять проблему, вибір, причину й альтернативи.
  Тексти моделей залишаються історичними повідомленнями, не дозволами.
- Статуси інструмента, актуальності охоплених файлів і перевірки мети розділені.
  Відсутність квитанції означає відсутність доказу, а не доведену брехню.
- Рутинні дозволені кроки проходять без додаткових запитів. Невідомий наслідок,
  зміна дозволів і передача приватного контексту мають видиме пояснення.

## Телефонне приймання

1. Створити невеликий Python-проєкт у Termux; записати рішення з причиною.
2. Запустити відому перевірку, внести виправлення, повторити ту саму перевірку.
3. Закрити застосунок; відкрити проєкт і продовжити з іншою локальною моделлю.
4. Перевірити збереження мети, рішення, відкритих зобов'язань і квитанцій.
5. Змінити файл поза Lumena; переконатися, що старий результат не став новим доказом.
6. Перервати дію; після відновлення перевірити UNKNOWN і відсутність автоповтору.
7. Перемкнути маршрут на хмарний: приватний canary не має залишити телефон без
   явного дозволу власника. Перезапуск не скасовує цю межу.
8. Виконати archive/reopen, перевірити збереження історії і replay barrier.

Зелений CI підтверджує код і тести на CI, а фізична перевірка — поведінку телефона.
Поки остання не виконана, статус фізичного приймання залишається NOT_RUN.
Робота з мільйонними репозиторіями та навчання ваг моделей потребують окремого
вимірювання; V1 не видає їх за виконану властивість.

## Межі поточного випуску

- Картка має бюджет 1200 символів; повні записи залишаються в сховищах і приватному експорті.
- Актуальність охоплених source bytes не засвідчує виключені файли або Python-середовище.
  Старий goal digest без epoch позначається LEGACY_GOAL_REVISION; він не стає новим доказом.
- Власницька зміна мети/обмежень створює новий goal epoch і скасовує попередній дозвіл egress.
  Прапорець із переносного JSON сам не надає мережевих прав: потрібна device-local згода.
- Зовнішня модель отримує проєктний контекст лише після явного дозволу власника для всіх
  проєктів, представлених у сеансі. Дозвіл охоплює історію, рішення й результати; це ширший
  режим, ніж автоматична мінімальна CARD-передача, яку цей випуск не реалізує.
- Нові проєктні виклики навчають лише записи Coordinator/Fractal з явною прив'язкою до
  цього проєкту. Сирі результати, мовні фрази та похідні поради не публікуються у загальні
  Memory/Landscape/Web/Constitution-шари. Сеанс із приватною історією зберігає цю межу
  навіть після зняття вибору проєкту. Старі глобальні записи не мають доведеної приватної
  provenance; вони не додаються до проєктних запитів. Вбудована конституція та обмеження
  власника залишаються в захищеному контексті. Агрегатні лічильники якості залишаються.
- Семантичний пошук проєкту використовує лише точний project scope. Для Ollama Embedding
  потрібне окреме підтвердження локального маршруту в панелі пам'яті; його скасування
  зупиняє надсилання тексту провайдеру. Вбудована LiteRT-модель цього підтвердження не потребує.
- Автоматичний Android cloud backup і device transfer вимкнені для даних застосунку.
  Власник сам зберігає явну копію через наявні засоби експорту; перевстановлення без копії
  може втратити дані. Це не видаляє наявну пам'ять і не змінює ключ підпису APK.
- CAS для file.write/file.patch увімкнено для Local project workflow. Потрібен оновлений міст
  із file_cas_v1. Точковий patch прив'язується до hash повного файла після читання ділянки;
  повний overwrite потребує повного read-result. Новий файл перевіряється через ABSENT.
  Це кооперативна перевірка bridge, не ізоляція довільних Python/інших процесів.
- Журнал автоматично переносить закриті сегменти за відсутності активних/UNKNOWN writers.
  Ліміти: 32 сегменти / 256 MiB / 100000 delivery identities; на межі capture зупиняється,
  історія не стирається. Перегляд у моделі/панелі обмежено останніми 256 архівними діями
  плюс активним журналом; повні SQLite-сегменти є в експорті.
- Проєктні записи, витіснені робочими caps, зберігаються в окремому незмінному history archive
  ДО AtomicFile commit. Його ліміт 64 MiB; при відмові архіву активний стан зберігається.
- Архівні immutable views кешуються в процесі; при cold open перевіряються file SHA і chain,
  при зміні metadata файлів кеш оновлюється. Це контроль пошкодження app-private даних,
  не автентифікація проти довільного процесу з тим самим uid.
- Кнопка «Копія всіх проєктів» експортує workspace, евіковану історію та квитанції. Імпорт
  таких файлів у app-observed журнал відсутній; експорт не обіцяє автоматичного restore.
- Для phone update потрібен той самий ключ підпису. Оновлення APK не потребує uninstall.

## Як почати користуватися

1. Підписати CI APK тим самим власницьким ключем і встановити як оновлення.
2. Оновити `termux/bridge.py` через `bash termux/install_bridge.sh`; health має
   показувати `version=0.32` і `file_cas_v1`. Перезапустити старий bridge-процес.
3. Відкрити Проєкти, обрати каталог, мету та вид перевірки. Для повного журналу
   ввімкнути «Зберігати нові виклики локально».
4. Обрати вбудовану модель або підтвердити локальну Ollama в спільному журналі.
   Embedding-модель допомагає пошуку; вона не замінює чат-модель і не зберігає мету.
   Для Ollama Embedding підтвердити її окремий локальний маршрут у панелі пам'яті.
5. Записати важливе рішення з причиною. Працювати звичайними запитами; «Продовжити»
   прив'язує наступний запуск до обраного зобов'язання. Новий явний запит не підміняється
   випадковою старою відкритою задачею.
6. Для зовнішньої моделі явно обрати передачу проєктного контексту. Зміна мети
   потребує нової згоди. Старе pending-підтвердження не виконується під новою метою.
7. «Копія всіх проєктів» зберігає приватний ZIP; наявність експорту не звільняє квоту.

## Підпис CI2325 у Termux

Завантажити [UNSIGNED-Lumena-ci2325-signing-input](https://github.com/Kvazarbit/Lumena-Android/actions/runs/39249664832/artifacts/12187024918)
у телефонну папку Download. ZIP не розпаковувати. Наявні Java/keytool, aapt/aapt2 та
`~/.lumena/Lumena-signing.enc` використовуються як раніше. Команда бере скрипт із
перевіреного коміту; пароль запитується тільки в локальному терміналі:

```sh
curl -fL https://raw.githubusercontent.com/Kvazarbit/Lumena-Android/c5120f35023cd8e84eecd6f9ded5ebae3f13c7c9/scripts/sign_lumena.py -o "$HOME/sign_lumena_ci2325.py" &&
python "$HOME/sign_lumena_ci2325.py" --run-id 39249664832
```

Скрипт спочатку перевіряє походження CI, digest ZIP, APK і наявний сертифікат;
підписаний файл та команду відкриття покаже після завершення. Оновити наявну Lumena
цим APK без видалення застосунку.

Для файлових операцій потрібен Bridge 0.32. У вікні старого моста спочатку натиснути
Ctrl+C. Потім оновити код і запустити; наявна конфігурація й токен лишаються:

```sh
curl -fL https://raw.githubusercontent.com/Kvazarbit/Lumena-Android/c5120f35023cd8e84eecd6f9ded5ebae3f13c7c9/termux/bridge.py -o "$HOME/.lumena/bridge.py.new" &&
mv "$HOME/.lumena/bridge.py.new" "$HOME/.lumena/bridge.py" &&
chmod 700 "$HOME/.lumena/bridge.py" &&
python "$HOME/.lumena/bridge.py"
```
