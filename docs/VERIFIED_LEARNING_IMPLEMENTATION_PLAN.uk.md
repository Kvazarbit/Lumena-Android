Версія плану: 1.0. Репозиторій: `Kvazarbit/Lumena-Android`.
Гілка: `feature/causal-experience-v1`. PR: **#111, draft; merge тільки за окремою вказівкою власника**.
Перевірена вихідна точка: `08a5b8cb9053d4ff4b97c9855fa7dda407644874`, Android CI #1837 SUCCESS.

Це конкретизація [наявної дорожньої карти](cognitive-exoskeleton-roadmap.uk.md), а не заміна Constitution, ContextKernel, Coordinator, Prediction/Delta, Fractal Canvas, TinyJev або Laya. Позначки старої карти описують її історичні перевірки; вони не доводять готовність нового наскрізного сценарію.

## 1. Результат, заради якого робимо роботу

Після цього плану агент повинен зберігати не тільки тему проєкту, але й підтверджені факти виконання, актуальні обмеження користувача та перевірені способи роботи. Наступна модель повинна використовувати цей досвід без копіювання старих дозволів, виконаних команд і вигаданих висновків.

Повний цикл:

`намір → актуальні спостереження → прогноз → дозволена дія → фактичний результат → незалежна перевірка → оцінений епізод → навичка-кандидат → перевірка перенесення → обмежене застосування → контрприклад/перегляд`.

**Не є ціллю:** збільшити лічильник пам'яті, назвати всі правила ACTIVE, перенавчити ваги Gemma, надати Laya право виконання або заново створити акваріум. Робочий `aquarium.html` не є тестовим полігоном для руйнівних дій. Використовувати ізольовані fixtures.

## 2. П'ять різних шарів

| Шар | Уже наявна основа | Цільове доповнення |
|---|---|---|
| Незмінні принципи | ConstitutionKernel, ToolRegistry, ToolGate | Доказ незмінності повноважень на кожному етапі |
| Пам'ять цілей | WorkThread.kt, LocalSessionStore | Ціль окремо від поточного доручення; проєктна область і походження |
| Історичні факти | ContextKernel, CoordinatorExperienceStore | Обмежене представлення фактів для нового контексту, не новий журнал |
| Набуті навички | ConstitutionGenome, Fractal Canvas, Cause Ladder | Кваліфікація за результатом задачі, перенесенням і контрприкладами |
| Поточне виконання | AgentController, WorkflowRunner, ExecutionEpochHistory | Свіжа перевірка, власний бюджет, дозволи і невідомі ефекти |

Історичне `file.read` доводить, що тоді відбулося читання. Воно не доводить, що файл незмінний зараз, прочитаний цілком або правильно проаналізований. Історичне `file.write: success` не доводить користь для проєкту.

## 3. Непорушні вимоги

1. Виконання дозволяє лише чинний контроль застосунку/телефону; пам'ять, ідентифікатори, хеші та модель не надають дозволів.
2. Поточне доручення обмежує довгу ціль. «Зараз тільки прочитай» не успадковує «виправ файл» із минулого.
3. Новий execution epoch не очищає знання про невідомий ефект попередньої дії. Потрібне узгодження фактичного стану, а не сліпий повтор.
4. Факт виконання, правильність результату, поточна свіжість і право на нову дію — чотири різні властивості.
5. Відсутній запис не означає «дії не було»; обрізана історія повинна позначати пропуски.
6. Модельна гіпотеза не стає доказом через повторення. Різні назви моделей не означають незалежні джерела.
7. Raw stdout, секрети, токени, приватні URL та ключі підпису не переносяться автоматично в довгу/соціальну пам'ять або хмарний prompt.
8. UNKNOWN, CONTESTED, негативні приклади й відкликані правила не стискаються в SUCCESS.
9. Проходження CI не дорівнює перевірці APK на телефоні або доказу покращення інтелекту.
10. Конституційне HARD-ядро не змінюється з досвіду. Оцінена навичка лишається рекомендацією під чинними перевірками.

## 4. Як виконувати план слабшій моделі

Працюй лише над першим незавершеним етапом, залежності якого підтверджені. Не переходь на наступний етап через оптимістичний опис.

Перед змінами прочитай поточні файли, перевір HEAD, `git status` і тести. Нові зміни інших авторів не перезаписуй. Відсутню функцію чи шлях спочатку знайди в дереві репозиторію. Файли нижче, явно позначені «нові», створюються лише після перевірки відсутності дубля.

Для кожної задачі: сформулюй очікуваний результат → додай тест на помилку → покажи, що він виявляє проблему/відсутню реалізацію → внеси мінімальну зміну → запусти вузькі тести → повний CI → запиши факти. Не змінюй очікування тесту лише заради зеленого результату. Контрприклад має залишатися в наборі.

Не замінюй великий файл заготовкою. Не створюй новий store, якщо достатньо проєкції існуючого. Не «виправляй» проблему збільшенням бюджету, повторною установкою APK або додатковою фразою в system prompt без тесту причинного механізму.

Підсумок кожного етапу містить: точний commit, змінені файли, виконані команди, число тестів, failures, посилання CI, що НЕ перевірено, наступний крок. `PASS` має область: `UNIT`, `INTEGRATION`, `CI`, `PHONE` або `UTILITY`.

### Робочі команди

У checkout з налаштованими JDK 17, Gradle 8.9 та Android SDK, як у `.github/workflows/android.yml`:

```bash
git status --short
git rev-parse HEAD
gradle --max-workers=2 :app:testDebugUnitTest --tests 'com.lumena.android.agent.core.HistoricalExecutionFactsTest'
gradle --max-workers=2 :app:testDebugUnitTest --tests 'com.lumena.android.agent.core.HistoricalExecutionFactsKernelTest'
gradle --max-workers=2 testDebugUnitTest
python scripts/mutation_recovery_probe.py
gradle --max-workers=2 assembleRelease
```

Якщо SDK/Gradle відсутні, не записуй `PASS`: використовуй наявний Android CI і зберігай його результат. Host `native-smoke` та bridge tests теж повинні пройти. Не припускай існування `gradlew`: поточний CI використовує `gradle`.

### Універсальний шлюз етапу

Кожен S01–S12 проходить: позитивний тест, негативний тест, перевірку сумісності, перевірку відсутності нових повноважень, профільні тести та exact-head Android CI. Для runtime-етапів додається phone-тест у зазначеній нижче групі. Після failure — виправлення того самого етапу, не перехід далі.

Один завершений набір code + tests + docs — один логічний етап. Дрібні технічні commits не є окремими прийнятими етапами. Не роби десятки однакових CI-запитів поспіль: перевір результат при зміні стану або після іншої корисної роботи.

## S01. Історичні факти без старої влади на виконання

**Реалізація цього першого зрізу:** новий `agent/core/HistoricalExecutionFacts.kt`; тести `HistoricalExecutionFactsTest.kt` і `HistoricalExecutionFactsKernelTest.kt`.

Використати існуючі `ContextKernelState` та `ActionEvidence`, не створювати паралельний журнал. `capture(sourceTaskId, kernel)` повертає типізовану проєкцію; `render(snapshot, maxChars)` готує обмежений текст без raw target/args/output/goal/model prose.

Поля: source-task reference; evidence ID; canonical-looking tool name; OBSERVE/ACT/VERIFY; SUCCESS/FAILURE; target correlation reference; digest результату; **task-local** revision; кількість пропущених записів; прапорець невідомого результату; історична кількість незавершених перевірок. Вихід не містить executable request, approval, budget чи training reward.

Не називати digest `ContextKernel` хешем файла: зараз це digest результату інструмента, а не повних байтів артефакту. Кореляційний SHA target не є шифруванням і може піддаватися словниковому відновленню; до хмарної/соціальної доставки потрібна окрема privacy-перевірка S02/S11.

Невідомий виклик не стає success/failure. Дублікати одного evidence ID не множать факти; суперечливі дублікати дають CONTESTED і не публікують позитивних фактів. Невалідний source дає INVALID_SOURCE. Обмеження першої версії: 12 фактів на проєкцію, максимум 4096 символів; за надто малого бюджету повернути порожній рядок, а не відрізати пояснення меж довіри.

**Тести:** 24 чисті перевірки проєкції та 4 тести з реальним ContextKernel: успіх, failure з можливими побічними ефектами, in-flight UNKNOWN, порожня/обрізана історія, duplicate/conflict, різні task ID, зловмисні рядки, невалідні digests, ліміти, незмінність source, незакритий новий GoalContract.

**Приймання:** вузькі тести й exact-head CI пройшли. **Важлива межа:** цей етап створює компонент, але НЕ підключає його до UI, prompt, persistent store або навчання. Історична амнезія на телефоні ще не оголошується виправленою.

**Відкат:** видалити лише новий компонент і його тести звичайним revert, не force-push.

## S02. Підключити факти до існуючої пам'яті сесії

**Файли:** `settings/LocalSessionStore.kt`, `ollama/ExecutionEpochHistory.kt`, точки збереження/відновлення в `ui/WorkflowChatScreen.kt`; інтеграційні тести. Використати existing HistoryTree/StateVault/Coordinator, а не глобальний singleton на всі проєкти.

1. Додати backward-compatible optional поле історичних посилань/проєкцій з явними source task, source device/install та project/branch scope. Старий JSON читається з порожнім полем.
2. Захоплювати факти тільки з app-owned kernel на реальному переході після tool result і перед заміною currentTask. Повторне збереження ідентичного task/event не множить записи.
3. Зберігати bounded набір, спочатку максимум 8 задач × 12 фактів. Окремий індекс посилань на існуючий журнал дозволяє дочитати втрачений контекст. Пропуски відображати, не вигадувати події.
4. До `ExecutionEpochHistory.rebuild` подавати факти явним аргументом. Пам'ять цілі та історичні факти відокремити від поточного user turn і службових директив. Не витягувати старий raw TOOL_RESULT з прозового чату.
5. При імпорті/відновленні зі стороннього джерела походження стає IMPORTED_ADVISORY, а не LOCAL_CURRENT. Чинний kernel не наповнюється старими подіями для задоволення нового контракту.
6. Капсула не містить попереднього `Continue this task`, old budget або pending tool command. Інформація про UNKNOWN лишається фактом для S03, а не дозволом повторення.

**Тести:** A: file.read → B: інша задача → A: запит про минулі дії; знайдено source receipt, а новий task має нуль виконаних дій. Зміна branch не змішує records; same e1 in two tasks не колізія; store round-trip; старий JSON; обрізання; пошкодження з quarantine/report замість мовчазного «нічого не було»; restore не відновлює approvals. Зловмисний excerpt не з'являється у prompt.

**Приймання:** справжній шлях save → load → rebuild перевірений; не лише тест проєктора. UI показує, що відомості історичні. **Phone gate A:** після S02+S03, одна установка, тест на fixtures. **Відкат:** вимкнути подачу нових проєкцій; зберегти журнал і backward-compatible поле.

## S03. Поточний намір, обмеження й UNKNOWN_EFFECT

**Файли:** WorkThread, TaskIntentRouter, GoalContract, AgentController, ToolGate/ToolRegistry та відповідні runtime-перевірки.

Ввести спільний типізований `EffectiveTaskPolicy`: довга ціль; поточне доручення; дозволені класи ефектів; явно заборонені інструменти; scope; походження; unresolved effects. Модель може запропонувати інтерпретацію, але не схвалити власний дозвіл. Неоднозначну мутацію не виконувати до уточнення/належного погодження.

Усі шари використовують одну нормалізовану політику. Не вирішувати одну й ту саму заборону незалежними substring-правилами. Контролер не додає mandatory mutation до read-only; gate відхиляє mutation/execution, не змінюючи файл і не витрачаючи tool slot як успішне виконання. `inspect.batch` перевіряє кожен child.

Знати про можливий незавершений ефект потрібно між epoch. Додати reconciliation-посилання на task/request, а не переносити approval. Повторне виконання такого самого мутуючого request не стає дозволеним через новий task ID. Read-only перевірка фактичного стану може закрити невизначеність; сам текст моделі — ні.

**Тести:** UA/RU/PL/EN; заперечення списку, лапки й цитата, «не зараз», виправлена пізніша пряма вказівка, старий root «зміни» + current «тільки прочитай», позитивний request після негативного, несумісні вказівки → уточнення. Деструктивна дія через file.write, file.patch, Python, Git та вкладений batch не обходить політику. UNKNOWN write → new epoch → same write не повторюється автоматично. Звичайне дозволене читання працює.

**Приймання:** нуль несанкціонованих змін у негативному наборі; правильні зміни не блокуються безпідставно. **Відкат:** revert конкретної policy-зміни, залишити консервативний stop при невизначеності, не дозволяти все як fallback.

## S04. Повнота читання та версія джерела

**Файли:** `termux/bridge.py` file.read, ToolResult metadata/codec, ContextKernel, GoalContract, context builder; bridge/JVM тести.

Додати типізоване `ReadCoverage`: target identity, artifact SHA-256 повних байтів або явно null, start/end/total lines, EOF, truncation на bridge і на model-delivery шарі, next range, source encoding. Хеш рахує довірений код; якщо весь файл не хешувався — не вигадувати SHA. Digest частини не підміняє digest файла.

Після обрізання prompt модель повинна бачити доставлений діапазон, а не «успішно прочитано весь файл». Покриття об'єднувати лише для того самого target і version. Зміна файла між читаннями робить старе покриття неактуальним. Для вузького питання достатньо релевантного діапазону; для повного аналізу потрібне заявлене покриття. Не змушувати завжди читати всі великі файли.

**Тести:** 100/600 рядків не дають full-read; file A не закриває критерій file B; прогалини між ranges; нова версія між slices; UTF-8 і CRLF; порожній файл; metadata без хешування; oversized stdout; missing next range; prompt truncation після повного bridge read. Для акваріума константи не доводять реалізацію jump/drag. Повторне читання того самого початку не додає покриття.

**Приймання:** кожен висновок про вміст має target/range/version; невидимий код лишається UNKNOWN. **Відкат:** старі результати читаються як coverage UNKNOWN, не як FULL.

## S05. Захищена зміна наявних файлів

**Файли:** bridge file.write/file.patch, policy і metadata; тести тільки у temp fixtures.

Підготувати candidate у тимчасовому файлі; перевірити expected source hash; зберегти перевірювану копію; виконати atomic replace на тому самому filesystem; перечитати output hash; пов'язати receipts до/після. При конкурентній зміні — відмовитися без перезапису. Не покладатися лише на ім'я backup.

Значне скорочення, видалення entrypoint, заміна програмного файла заготовкою або відсутність дозволеного rewrite — сигнали додаткової перевірки. Розмір сам по собі не є доказом поломки: законний рефакторинг/видалення після погодження і тестів повинні працювати.

Накласти захист на всі заявлені шляхи запису. Python, shell/Git та native виконання не стають ізольованими лише тому, що список шляхів дозволений у UI. Де повне обмеження ефектів технічно відсутнє, показати це й вимагати окремого погодження; не називати такий виклик read-only.

**Тести:** файл із 35 KB логіки → 974-byte placeholder; stale expected hash; symlink/path traversal; failure під час write/fsync/rename; нестача місця; concurrent write; partial effect; rollback із checksum; legitimate full rewrite; backup і working file не зникають разом. Межі регресії перевіряти функціональними fixtures, не тільки пошуком рядка.

**Приймання:** невдале застосування залишає попередню версію або явно позначений recoverable state; жодного silent truncation. **Відкат:** перевірений preimage з source/target hashes, після нього незалежна перевірка, без видалення доказів помилки.

## S06. Незалежна перевірка користувацького результату

**Файли:** GoalContract/EvidenceProjectApplication, typed verifier adapters, fixture suites.

Розділити `tool_success`, `artifact_valid`, `behavior_verified`, `user_goal_satisfied`. Read-only задача може завершитися після достатньої перевірки прочитаного. Зміна коду потребує конкретних postconditions. `DONE` не автоматично стає позитивним навчальним label.

Verifier прив'язаний до того самого artifact hash та recipe version. Умови не можна змінити заднім числом після результату. Тести, написані тією самою моделлю, корисні, але самі по собі не незалежний oracle; використовувати заздалегідь зафіксовані fixtures, контрприклади та hidden evaluation set.

**Тести:** syntax PASS + behavior FAIL; exit 0 + 0 tests; stdout «PASS» без postcondition; відредагований після перевірки файл; wrong target; stale digest; legitimate directory listing; вузьке читання; read-only prose vs JSON не змінює доказовість; незавершена властивість → PARTIAL. Не послаблювати completion gates заради приємного тексту.

**Приймання:** у наборі негативних fixtures нуль false-DONE для заявлених postconditions. **Phone gate B:** S04–S06 разом на тестових копіях, не новий APK на кожен рядок. **Відкат:** verifier може повернути UNKNOWN; це краще за автоматичний PASS.

## S07. Оцінений епізод і урок

**Файли:** існуючі CoordinatorExperience/Prediction Delta/Fractal store та нові optional поля, не другий ledger.

Епізод містить task/project/device/model provenance; початкові умови; очікування ДО дії; refs на дії й наслідки; незалежний verifier ref/version; outcome SUCCESS/FAILURE/UNKNOWN/CONTESTED; витрати; допомогу користувача; правила, які реально були доставлені. Завершувати епізод ідемпотентно.

Recovery із backup має оцінку «стан відновлено», а не «помилковий запис був корисним». UNKNOWN не входить у denominator accuracy як failure чи success; звітувати його кількість окремо. Старі записи без postcondition не підвищувати заднім числом.

**Тести:** повторна доставка одного result; process restart перед closure; successful write + failed behavior; user rescue; imported example; суперечливий verifier; ручне `DONE`; stale tests; одна задача з 10 retry не стає 10 незалежними уроками.

**Приймання:** один terminal episode відповідає одному виміряному результату; lineage не втрачається. **Відкат:** вимкнути використання нових labels, не стирати raw source ledger.

## S08. Контекстні навички та контрприклади

**Файли:** ConstitutionGenome/Fractal retrieval та кваліфікатор навичок.

Навичка: rule ID/version; умови застосування; рекомендований метод; очікуваний postcondition; source episodes; незалежні контексти; негативні приклади; scope; environmental fingerprint; expiry/revocation; статус. Не зберігати executable команду з секретами як правило.

Стани: CANDIDATE_SHADOW → EVALUATED_ADVISORY → SUSPENDED/CONTESTED/RETIRED. Назви зіставити з чинними enum, не створювати несумісну паралельну модель. Мінімум кількох source tasks і проєктів — необхідна умова перенесення, але НЕ достатній доказ якості. Повторний однаковий seed не незалежна перевірка.

У прикладі акваріума урок — «перед продовженням не замінюй існуючу логіку заглушкою без обґрунтованого rewrite і перевірки». Це має переноситися на Python-проєкт, а не бути правилом для слова aquarium.

**Тести:** duplicate episodes; один пристрій з двома назвами моделей; несумісне середовище; expiry; відкликання; суперечливий випадок; scoped виняток; рядок-ін'єкція в рекомендації; новий counterexample припиняє пораду; запит на дозволений альтернативний метод не блокується правилом-кандидатом.

**Приймання:** порада має пояснення походження і може бути вимкнена; ніяких нових прав. **Відкат:** suspend конкретну версію навички, не міняти HARD.

## S09. Довести користь: paired A/B на нових задачах

**Основа:** перевикористати існуючі arena/evaluation механізми; спочатку перевірити їх придатність, не дублювати.

A і B мають однакову модель/версію, контекстний і tool бюджет, guard rules, verifier, fixtures та середовище. A без досліджуваних learned tips; B з ними. Базові правила безпеки НЕ відключати в A. Порядок/seed пар реєструвати заздалегідь. Розділити навчальні, development і holdout задачі за походженням, не тільки ім'ям файла.

Початковий експериментальний набір: щонайменше 3 родини (JS/HTML, Python data pipeline, конфігураційний проєкт), 20 різних задач у родині; повтори для стохастичної моделі. Це запропонований обсяг пілота, не обґрунтована наперед статистична потужність. Після вимірювання дисперсії обсяг переглянути ДО наступного holdout, а не до отримання бажаної відповіді.

Основна метрика — verifier-defined task success. Окремо: false-DONE, unauthorized mutations, repeated known errors, user interventions, model/tool calls, tokens, time, UNKNOWN coverage. Звітувати парну різницю й довірчий інтервал, raw counts і failures; не ховати шкоду у середньому reward. Жодної гарантії 95% наперед.

**Тести:** детермінований evaluator на синтетичних парних outcomes; перемішування порядку не змінює рахунок; missing runs не стають success; knowledge leakage; однакові права в A/B; штучно шкідлива порада виявляється; memory hit без delivery/use не рахується utility; некоректний verifier робить оцінку INVALID, не покращує score.

**Приймання:** відсутні порушення прав у контрольному наборі; напрямок/невизначеність користі явно показані. Якщо перевага не доведена — NO_DEMONSTRATED_BENEFIT, навичка не просувається. **Відкат:** повернути retrieval без досліджуваної навички.

## S10. Кероване зростання набутої конституції

Операційний принцип набуває статусу лише за доказами з S07–S09, із rationale, scope, counterexamples і version diff. Зміна відповідає «як краще працювати», не «які нові права маю».

Зміни довіри, privacy, дозволів, незмінних правил або пріоритетів власника потребують окремої явної процедури погодження і не входять в автопромоцію. Не називати статистичну популярність моральною істиною. Зберігати пояснення «чому правило існує» і причини його перегляду.

**Тести:** повторені tool successes без goal utility не активують правило; imported evidence alone не промотує; rule conflicts with current user limit → недоступне; rollback не воскресає revoked tip; HARD fingerprint незмінний; жодне правило не вмикає Laya/tool execution.

**Приймання:** версії відтворювані, видимі й оборотні; activation не означає permission. **Відкат:** повернення попередньої валідної learned-версії із збереженням revocations.

## S11. Стиснення, приватність і соціальний перенос

Зберігати окремо: факти, узагальнення, гіпотези, негативні уроки і суперечності. Summary — похідна проєкція з посиланнями, не новий доказ. Eviction не може приховано видалити єдиний контрприклад або unresolved effect; захистити такі класи квотами/посиланнями та показати неповноту.

Portable package: schema version, source device/task/model refs, rule lineage, verifier recipe, environment, optional content hashes, підписи/цілісність де доступні, privacy policy і статус source-device advisory. Цілісність пакета не доводить правдивість джерела і не дає повноважень. Імпорт не переносить approvals, tokens, ключі підпису, локальні абсолютні шляхи або активний kernel.

**Тести:** 10 000 fixture episodes і bounded storage; збереження WORST/CONTESTED; видалене source evidence робить derived advice недійсним; malicious capsule; schema upgrade; corrupt package; cross-device replay; duplicated shared experience; multi-model aliases; secrets у URL/логах; source revoked after import; неповний пакет не маскується як повний.

**Приймання:** імпорт допомагає пошуку кандидатів, але вимагає локальної revalidation; ліміти виміряні на цільовому Android. **Відкат:** відключити імпортовану версію і залежні поради; не видаляти локальні власні факти.

## S12. Наскрізне приймання й передача в експлуатацію

Один фінальний canary після інтегрованих тестів; власник підписує APK тим самим ключем. Перед установкою перевірити точний artifact SHA, package/version, certificate та apksigner. Installer intent не є підтвердженням установки. Окремий diagnostic підтверджує запущену версію.

Сценарій на ізольованих файлах:

1. Створення користувацької цілі A з read-only кроком; повне/часткове читання відображене чесно.
2. Інша задача B; потім повернення до A по імені та коротке «продовж».
3. Запит «що вже було зроблено?» відтворює історичні факти, не видає їх за поточний стан.
4. Контрольована помилка, перезапуск застосунку, PARTIAL і UNKNOWN; відсутній сліпий replay.
5. Зміна моделі, закриття/відкриття історичної гілки, оновлення APK, backup/restore.
6. Лише погоджена зміна fixture; незалежний verifier; епізод → навичка → новий проєкт.
7. Контрприклад/відкликання; порада припиняється без зникнення доказів.

**Приймання:** всі критичні негативні випадки пройшли; hash робочого акваріума до/після незмінний; помилки читання/протоколу не маскуються. P50/P95 затримок, пам'ять і розмір store виміряні, а бюджет узгоджений. Вказати режим: deterministic replay, mock model, real model, real phone — не змішувати.

Фінальний висновок має три незалежні статуси: FUNCTIONAL_ACCEPTANCE, SAFETY_TESTS, DEMONSTRATED_UTILITY. «Ідеальна» або «готова на 100%» конституція не є тестованим результатом. Merge — лише після окремої вказівки власника.

**Відкат:** зупинити тестовий запуск, залишити попередній перевірений APK та копію app-state; невідомі ефекти узгодити до відновлення роботи. Не очищати сховища і не відновлювати старі дозволи автоматично.
