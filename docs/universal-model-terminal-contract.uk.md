# Єдина конституція й робота моделей з Termux

Це спільний контракт **моделей, підключених до Lumena**: локальна GGUF-модель,
Ollama та зовнішній координатор Companion. Це пропозиція універсальної основи,
а не вже ухвалений світовий стандарт. Назва моделі й місце отримання її ваг
не дають їй додаткових повноважень. Embedding-модель окремо будує вектори пошуку;
команди обирає генеративна модель, а виконує застосунок.

Джерело законів — наявні `ConstitutionCharter` (14 статей) і
`ConstitutionCapsule`; їхній зміст цим етапом не змінюється. Новий
`ModelOperatingContract` поєднує їх із практичним `TerminalWorkflowProtocol`.
У контексті є версія контракту й відбиток хартії. Однаковий текст отримують
локальний агент і Companion; коротка прив'язка до хартії та капсула захищені
від обрізання в кожній задачі. Для коду й зареєстрованих проєктів також
захищений протокол роботи з терміналом.

```text
Єдина основа Lumena
├── Власник: мета, обмеження, згода на конкретну дію
├── Хартія: повноваження, докази, права й обов'язки
├── Генеративна модель з хабу: запропонувати наступну JSON-дію
├── Ядро: перевірити інструмент, межі проєкту та дозвіл
├── Termux: виконати зареєстрований інструмент
├── Докази: результат → перевірка зміненого об'єкта → чесний звіт
└── Живий досвід
    ├── успіх і помилка з умовами та походженням
    ├── UNKNOWN окремо, без вигаданої оцінки успіху
    ├── поради для наступної моделі, локальна переперевірка
    └── пропозиція зміни закону → перегляд власником → код і тести
```

## Як Люмена користується терміналом

1. Відкрити проєкт у «Проєкти». Вказати каталог Termux, мету, обмеження та
   профіль перевірки. Оновити й перезапустити Bridge 0.31 або новіший:
   `bash termux/install_bridge.sh`, зупинити попередній процес, тоді
   `python ~/.lumena/bridge.py`. У `health` перевірити `python_fresh_bytecode_v1`.
2. Написати, наприклад: «У цьому проєкті виправ обчислення суми в main.py,
   збережи API, додай перевірку й запусти всі тести».
3. Люмена оглядає проєкт і читає потрібний файл; пропонує `file.patch` або
   `file.write`. Власник погоджує зміни та виконання коду через наявний інтерфейс.
4. Для Python-проєкту з профілем `PYTHON_TESTS` запускає
   `python.tests {"cwd":".","argv":"-q"}`. Потрібен свіжий непорожній
   JUnit-звіт; перевірка синтаксису сама по собі не доводить проходження тестів.
5. Якщо власник попросив коміт, переглядає `git.diff`, виконує `git.add` і
   `git.commit`. Коміт не замінює перевірку працездатності.
6. Зберігає результат, докази й незавершену роботу в проєкті. Інша модель
   отримує той самий контракт і контекст; історичний успіх потребує свіжої перевірки.

`python.run` запускає наявний файл `.py`: застосунок показує попередній перегляд
і прив'язує згоду до SHA-256. Модель не має створювати собі хеш дозволу.
Неоднозначний результат зміни означає спершу оглянути стан, потім відновлювати роботу.

Цей етап використовує наявні інструменти файлів, Git і Python. Довільний Bash,
встановлення пакетів, Gradle/npm та повноцінна інтерактивна PTY-сесія потребують
окремих інструментів із явними контрактами. Якщо потрібного інструмента немає,
Люмена повинна повідомити конкретну межу й залишити задачу частковою.

## Що означає «жива»

Перевірений досвід покращує вибір дій і передається між моделями через контекст
проєкту, а не через зміну ваг моделі. Згода кількох моделей не доводить закон.
Моделі можуть пропонувати зміни; текст із README, результат інструмента чи
імпортований досвід не можуть самі змінити дозволи або жорстку хартію.

Наявні PARTIAL/PENDING у хартії залишаються видимими: зокрема автоматичний строк
дії кожного вивченого правила й повний holdout для окремих правил ще не завершені.
Termux запускає код з UID користувача; контракти не створюють ізоляцію процесів.
Це не обіцянка, що будь-яка мала модель завжди правильно виконає інструкцію.

## Перевірка цього етапу

- JVM: спільний контракт Local/Companion, збереження конституції у звичайному
  чаті й термінальних інструкцій при скороченні контексту Ollama/embedded.
- Production runner зі сценарними моделями: читання → зміна після згоди →
  повні тести після згоди → DONE; UNKNOWN не стає навчальним успіхом.
- Реальний Bridge у тимчасовому каталозі: контрольна помилка Python →
  виправлення → успішний запуск → локальний Git-коміт; старий SHA-дозвіл
  після зміни скрипту відхиляється; вигадана згода конституції не дозволяє shell.
- Регресія свіжості коду: навмисно застарілий `.pyc`, однакові розмір і mtime
  до/після виправлення. Кожен запуск Python використовує новий простір кешу
  і не пише байткод; інакше тест міг би виконати попередню версію імпорту.
- Перевірка на телефоні: підписати APK власним ключем, відкрити тестовий проєкт,
  повторити цей цикл локальною моделлю та Ollama. До цього фізичну роботу
  конкретної моделі й Android lifecycle не можна вважати підтвердженими.

Довідковий desktop-застосунок не змінюється.
