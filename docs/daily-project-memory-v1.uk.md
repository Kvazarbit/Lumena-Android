# Щоденна робота з локальною пам'яттю — етап V1

Мета: відкрити вибраний проєкт після перерви, відновити його робочий стан і
отримати доречні підказки з локального досвіду перед відповіддю чат-моделі.
Фактичне виконання, дозволи й перевірки результату залишаються окремими.

## Дерево реалізації

1. Намір власника
   - опис, цитата, приклад коду та історичний звіт не створюють required tools;
   - явна поточна команда має пріоритет над старою метою;
   - позитивні команди, заборони, списки перевірок і назви файлів збережені;
   - повторне безрезультатне перепланування завершується PARTIAL зі збереженими receipts;
   - у контекст передається точна версія та commit APK для порівняння з прочитаним репозиторієм.
2. Постійна модель
   - backend, Ollama tag і перемикач пам'яті чату зберігаються на пристрої;
   - для наявної імпортованої копії без старого backend preference обирається LiteRT;
   - SHA-256 приватної копії, початкова назва та підказка джерела імпорту;
   - збережений файл та успішний минулий запуск не означають постійно зайняту RAM.
3. Чат і локальний пошук
   - одна сесія відбору пам'яті на запуск користувацького запиту;
   - до чотирьох нових структурованих принципів оновлюються за ревізіями;
   - пошук тільки серед GLOBAL і поточного проєкту, окремий простір для кожного digest моделі;
   - до трьох підказок з джерелом, ревізією та кількістю доказів;
   - підказки є недовіреними DATA і не дають дозволів чи доказу DONE;
   - при недоступності embedding звичайний контекст проєкту залишається працездатним.
4. Індексація після переходу в чат
   - запущена власником унікальна WorkManager задача, до 48 принципів;
   - пакет до чотирьох, запис у SQLite після кожного пакета;
   - закриття налаштувань не скасовує задачу;
   - після зупинки/перезапуску вже записані ревізії пропускаються при продовженні;
   - STOP, вимкнення модуля та зміна моделі перевіряються до нового запису;
   - обмеження низької батареї та нестачі сховища. Android може відкласти виконання.
5. Незмінні опори
   - проєктні цілі, обмеження, рішення, handoff і receipts продовжують зберігатися ProjectWorkspace;
   - першоджерела Fractal/Genome не переписуються векторами;
   - модель та індекс не змішуються з новим signing identity або автоматичними дозволами;
   - вага моделі не завантажується автоматично; навчання ваг у цей етап не входить.

## Перевірка

Колишні 16 діагностичних assertions тепер повинні пройти без очікуваних відмов.
Додатково перевіряються відновлення перерваного пакета, scope ізоляція,
вимкнення recall, недоступний JNI, постійний backend, підключення пам'яті до
реального WorkflowRunner та неможливість надати мережевий дозвіл через пам'ять.
Фальшиві провайдери перевіряють керування сесією, SQLite і контекст; це не
доказ якості чи працездатності справжніх 270M ваг на фізичному телефоні.

## Користування та приймання на телефоні

1. Зберегти StateVault і встановити оновлення з тим самим сертифікатом власника, без uninstall.
2. Увімкнути модуль семантичної пам'яті, обрати LiteRT CPU. Наявна приватна копія має відобразитися.
3. Якщо копії немає, імпортувати .litertlm через Android. Перевірити початкову назву й джерело.
4. Виконати справжній CPU smoke: лише числовий вектор підтверджує READY.
5. Увімкнути «Використовувати локальну пам'ять у чаті». Обрати потрібний проєкт.
6. Запустити індексацію, повернутися в чат, потім відкрити налаштування: backend не скидається.
7. Перезапустити застосунок: перевірити модель, проєкт, незавершену задачу та збережені пакети.
8. Після перевіреної роботи на одному проєкті відкрити інший: приватні принципи першого не мають з'явитися.

Owner signing виконується існуючим scripts/sign_lumena.py після успішного CI
точного commit. Без власницького підпису CI APK не можна встановити.
Цей документ є планом і протоколом приймання; результати CI та телефона фіксуються окремо.
