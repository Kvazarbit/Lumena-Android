# Як працювати з проєктом на Android

## Підготовка

Потрібні APK з цієї гілки, Termux bridge **0.30**, Git і Python/pytest у Termux.
APK і bridge оновлюються окремо. Порядок встановлення bridge описаний у
[README.md](../README.md#termux-bridge); використовуй bridge.py з того самого
коміту, що й APK. Новий APK поверх bridge 0.29 не додає серверні інструменти.
Не видаляй застосунок перед оновленням: приватна пам'ять зберігається при
оновленні APK з тим самим власницьким підписом. Спочатку зроби копію StateVault.

Робоча копія має бути на телефоні в `LUMENA_WORKSPACE` bridge. Наприклад,
`demo` означає підкаталог `demo` цього простору. Windows-шлях автоматично не
передається на телефон. Явно підключені `@alias` доступні тільки для читання.
Каталог V1 задається без пробілів. Якщо його ще немає, першою задачею попроси
створити каталог `.` у вибраному проєкті, потім потрібні файли.

Для Python-проєкту встанови `pytest` у вибраному середовищі Termux. Перевір
підключення bridge й чат-модель у налаштуваннях Lumena. Ollama або GGUF — спосіб
генерації відповідей; embedding-рушій — окремий пошук пам'яті. Базовий цикл
проєкту працює без embedding-моделі. Локальна ОС контексту зберігається на
телефоні; якщо вибрана хмарна чат-модель, відібраний контекст надсилається їй.

## Перший робочий цикл

1. Відкрий **Проєкти → Додати проєкт**. Вкажи назву, каталог, мету й обмеження
   по одному на рядок. Правила звичайною мовою надходять у кожен запит;
   програмно виконуються лише обмеження, які розпізнає компілятор політики.
2. Вибери **Python + pytest** для Python або **Перечитати файли** для огляду
   текстових проєктів. Другий профіль підтверджує огляд змін, а не роботу програми.
3. Дай невелику конкретну задачу, наприклад: «Створи main.py з функцією
   add(a,b), додай тести й запусти повний pytest проєкту».
4. Lumena спочатку огляне вибраний репозиторій, потім запитає дозвіл на зміни
   та виконання. У дозволі перевір каталог і дію. Підтвердження для однієї
   задачі не переноситься на наступну.
5. Після змін Python-профіль вимагає повний запуск `python.tests` у корені
   проєкту з непорожнім успішним JUnit-звітом. Читання, syntax_check чи один
   вибраний тест цього не замінюють. `DONE` засвідчує виконані операційні
   критерії, а не доводить правильність усіх вимог програми.
6. Якщо кроків не вистачило, відкрий **Проєкти → Відкриті задачі → Продовжити**.
   Підготовлений текст можна уточнити й надіслати. Створюється новий запуск зі
   свіжими перевірками та тим самим зобов'язанням у пам'яті.

Змінюй модель звичайним перемикачем у налаштуваннях. Наступний запуск отримає
локальні правила, відкриті зобов'язання, релевантні рішення та історичний звіт
попередньої моделі. Власницькі архітектурні рішення записуй у панелі:
**проблема → рішення → причина → альтернативи**. Старий звіт і згода моделей
не видаються за поточні докази чи дозвіл на інструменти.

## Перерва, невідомий результат і резервна копія

`PARTIAL`, `FAILED`, перервані та `UNKNOWN` задачі залишаються відкритими.
Після втрати зв'язку результат запису може бути невідомим: спочатку оглянь
фактичні файли/Git, потім вирішуй щодо повтору. Невідомий результат не дає
навчального голосу success/failure і не зникає від нового модельного кроку.
Після власної перевірки можна явно **Закрити зобов'язання**; позначка UNKNOWN
при цьому лишається в історії. Закрите зобов'язання можна відкрити знову.

Перемикання проєктів зберігає окремі діалоги та відкриває їх без запуску дій.
Нова задача в історії зберігає проєкт; нова тема починає звичайний чат.
StateVault включає паспорт, задачі, рішення й історію. Ваги моделей та робочі
файли репозиторію зберігай окремо. Відновлена копія не повертає старі дозволи.

## Робочі межі цього етапу

- До 16 проєктів, 32 відкритих і 128 останніх задач на проєкт, 64 рішення.
  Для кожної задачі зберігаються до 16 попередніх звітів запусків і 48 receipts.
  Відкриті задачі не викидаються заради ліміту. Після заповнення потрібне явне
  закриття або звуження роботи; архів рішень не перезаписується мовчки.
- Огляд читає до 1500 текстових файлів, 8 MiB загалом і 512 KiB на файл із
  часовим лімітом. Відомі назви секретних файлів, залежності й symlink
  відсіюються. Секрети всередині звичайного коду можуть потрапити в контекст.
- Пошук повертає шляхи, рядки, hash прочитаного джерела та явне обмеження
  покриття. Порожній результат не означає, що функції немає. Великі репозиторії
  переглядай по модулях; V1 не є повним LSP або доказом роботи з мільйоном рядків.
- Обов'язковий контекст не обрізається. Якщо він не вміщується у вікно моделі,
  робота зупиняється з поясненням: збільш контекст або звузь відкриті задачі.
  Для дуже малих локальних моделей це практичне обмеження.
- Шляхи інструментів прив'язані до проєкту. Запущений Python працює з правами
  Termux і не ізольований окремою ОС-пісочницею. Виконуй лише довірений код.
- Компіляція Kotlin/Gradle та інших мов на телефоні, синхронізація з ПК,
  паралельний форум агентів і навчання ваг не входять у V1.

## Перевірка на телефоні перед робочим використанням

Створи два тимчасові проєкти з різним `main.py`; перевір розділення діалогів
і шляхів. Зроби зміну з тестами, отримай `PARTIAL`, перезапусти APK, продовж
іншою моделлю та перевір збережені правила/рішення. Перевір помилковий тест і
оновлення файлу після успішного тесту: задача має вимагати нової перевірки.
Експортуй StateVault і перевір відновлення на тестових даних. CI перевіряє
програмні контракти; реальну швидкість, якість моделі та поведінку Android
після зупинення процесу треба прийняти на конкретному телефоні.

## Звідки взято метод перевірки

Приклад `TelegramTandemWay/old_TandemWay_2/back_003` використовувався тільки
для читання. Ідеї зіставлено з `tools/decision_memory.py`, `selective_memory.py`,
`selective_memory_v2.py`, `code_symbol_index.py`, `semantic_context_index.py`,
`context_evidence_runner.py` та `os05_freshness.py`.
Нові Android/bridge-тести написані окремо: відомо правильний початковий стан,
контрольна несуттєва зміна, точна семантична поломка й очікувана перевірка.
Помилка компіляції або інфраструктури не зараховується як спіймана регресія.
