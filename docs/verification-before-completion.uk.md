# Lumena · Verification Before Completion v1

## Навіщо

Детермінований локальний захист від `DONE` без підтвердженого результату.
Це **не** заміна `GoalContractPolicy`, `ContextKernel` або `ToolGate`.
Хмарна/локальна модель не має права перевизначати результат контролера.

## Джерела авторитету

1. `ContextKernel` записує фактичні результати виконання зареєстрованих інструментів. Саме `kernel.evidence`, а не текст моделі чи `toolUsed`, засвідчує наявність успішного TOOL_RESULT.
2. `GoalContractPolicy` визначає типізовані обов'язкові критерії задачі (наприклад, успішний `image.search`, читання джерела, перевірка зміненого Python-файлу).
3. `CompletionEvidenceGate` забороняє `DONE` для операційних задач без успішного локального TOOL_RESULT та для самостійного `покажи!` без об'єкта.
4. `ToolRegistry`/`ToolGate` керують дозволами. Жодна перевірка не дає моделі нових повноважень.

## Випадки

| Сценарій | Результат |
| --- | --- |
| `покажи!` як окрема задача без визначеного об'єкта | `PARTIAL`: запитати, що показати |
| `покажи!`, навіть після випадкового `system.time`, але без визначеної цілі | `PARTIAL` |
| `покажи!` після коректної задачі «знайди фото кота» | зберегти попередню візуальну ціль; `DONE` лише після відповідних критеріїв |
| `реалізуй` / `зроби` без успішного локального інструмента | `DONE` заборонено; повторна модельна корекція або `PARTIAL` |
| `toolUsed=true` без `kernel.evidence` | `DONE` заборонено |
| Звичайна відповідь «2+2 = 4» без інструментів | `DONE` дозволено |

## Межі доказів

- Успішне виконання інструмента **не дорівнює** семантичному успіху всієї задачі. Типізовані критерії залишаються необхідними; за відсутності покриття звіт має чітко вказувати, що перевірено, а що ні.
- Візуальний результат `image.search` може довести отримання зображень, але не доводить, що знайдені кадри точно відповідають задуму людини без незалежного візуального перегляду.
- При `PARTIAL`, `FAILED` або `UNKNOWN` не можна заявляти про успішне виконання.
- Це структурний захист, а не доказ когнітивного навчання. Поліпшення слід порівнювати в контрольованих експериментах (Layer Governor).
- Ніякого автоматичного доступу до приватних файлів, ключів, APK або `git merge` цей механізм не додає.

## Перевірка

`gradle --max-workers=2 testDebugUnitTest`, включно з
`CompletionEvidenceGateTest`, `NoEvidenceCompletionTest`,
`CompletionEvidenceTest` і наявними тестами GoalContract.

Далі потрібен окремий тест на реальному OnePlus після підписування й інсталяції,
тільки за дозволом власника. Власна модель не є незалежним свідком свого успіху.
