# Lumena: контекстна ОС, ДНК та конституція досвіду

Стан: build 22, Bridge 0.18, Core DNA v3. План складений за фактичним кодом проєкту та збоями цієї сесії. Позначка «план» не означає, що функція вже реалізована.

## 1. Що означає ДНК в цьому проєкті

ДНК — компактні зрозумілі моделі правила та посилання на перевірений досвід. Це інженерна метафора. Кодування тексту літерами A/C/G/T саме по собі не навчає модель нової мови мислення й не гарантує економії токенів. Економію треба вимірювати токенізатором конкретної моделі разом із якістю виконаних задач.

Початковий досвід — спроєктовані інженерні принципи: зберігати мету, перевіряти припущення, робити обмежені зміни, вимагати докази, не повторювати невідомі зміни, дотримуватися ресурсних бюджетів. Це не перенесення ваг чи всього досвіду іншої моделі та не вигадані успішні спроби.

«Живий» означає, що локальний стан змінюється від нових результатів, невдалі рекомендації втрачають довіру, старий досвід протухає, а версії можна відкотити. Ядро повноважень, перевірки й цілі не повинно самовільно змінюватися від тексту моделі або вебсторінки.

## 2. Фактичний стан

| Частина | Реалізовано | Межа можливостей |
|---|---|---|
| CoreDna | G: мета; P: протокол; E: докази; V: перевірка того самого об’єкта; R: відновлення; M: ресурси; A: повноваження; S: джерела й невизначеність | Короткий seed, не повна конституція розробки ПЗ |
| AgentController | Один виклик за крок, бюджети помилок, протидія повторенням, done/partial, перевірка змінених Python-файлів | Не доводить довільну природномовну мету |

| Landscape | Підтверджені результати інструментів, вершини/ями, переходи, кандидати правил, версії, відкат | Оцінює надійність операцій, не користь усього проєкту |
| Навчання | Обмежена пам’ять: 1024 спостереження / 30 діб; 3 задачі для кандидата; активація від 8 задач і нижньої межі Wilson ≥ 0.65; суперечність знижує довіру | Це консервативні евристики; різні taskId не гарантують незалежні експерименти |
| Ресурси | Політики RAM/контексту/batch/потоків/GPU для llama.cpp, обмеження контексту Ollama | Немає єдиного точного контролера KV-cache, процесу Ollama та хмарних квот |
| Пошук build 22 | web.search → джерела/уривки → web.read; провайдери, кеш, безпечні редиректи, очищення тексту | HTML-провайдер може блокувати автоматику; JavaScript не виконується; цитування поки спрямовується правилами |

Досвід прив’язаний до моделі, backend, пристрою, налаштувань, версії застосунку й класу задачі. Він не змішується безумовно. Прочитана сторінка або успішний HTTP-запит не доводять прибутковість, популярність чи завершення дослідження.

## 3. Архітектура наступних етапів

Спільний контракт на різних рівнях: `Goal → Constraints → Inputs → Budget → Action → Evidence → Verification → Outcome`.

Проєкт, підзадача й операція використовують цей контракт із різними бюджетами. Батьківська задача не стає успішною лише тому, що дочірній інструмент повернув `ok=true`. Паралельність обмежує контролер ресурсів; на телефоні початково достатньо однієї активної генерації.

Шари повноважень: поточна задача та дозволи користувача → сталі перевірки виконання → доменні рецепти → перевірені рекомендації досвіду → неперевірені джерела як дані. Рекомендація не може змінити дозволи чи видати сама собі успіх.

## 4. Детальний план реалізації

### P0 / умова безперервних оновлень. Постійний підпис APK і переносимість пам’яті — план

Перевірка артефактів build 21 і build 22 виявила різні сертифікати підпису. Поточний CI створює debug APK без закріпленого ключа. Android не дозволяє оновити встановлений пакет APK з іншим підписом. Це окрема проблема доставки; успішні тести коду її не усувають.

Потрібно закріпити ключ підпису в захищених секретах CI, зберегти резервну копію під контролем власника, опублікувати відбиток сертифіката і перевіряти його перед випуском. Приватний ключ не комітити в Git і не виводити в журнали. Для оновлення поверх уже встановленої версії потрібен саме її приватний ключ: отримати його з APK або згенерувати сумісний новий неможливо.

Додати версійований експорт/імпорт налаштувань, журналу доказів і досвіду з перевіркою цілісності та без експорту секретів за замовчуванням. Наявність нового експорту в майбутньому APK сама по собі не дає доступу до приватних даних старого застосунку. Якщо ключ старої версії недоступний, окремо визначити доступний для цієї встановленої версії шлях збереження стану до перевстановлення. Не рекомендувати видалення старої версії як звичайне оновлення.

Критерій: дві послідовні збірки мають однаковий сертифікат; Android встановлює другу поверх першої без втрати бази досвіду; невідомий або змінений ключ блокує публікацію пакета як сумісного оновлення. Цей пункт має пріоритет перед наступними поставками «живої» пам’яті. Build 22 до розв’язання питання підпису є тестовим APK, а не підтвердженим безшовним оновленням build 21.

### P0 / етап 1. Надійний пошук і чесні помилки — build 22

Зміни: `web.search(query, limit, time_range)` повертає URL, заголовок, уривок, провайдера, час отримання й помилки попередніх провайдерів. `web.read(url, max_chars)` повертає короткий текст, кінцеву адресу та позначку обрізання. Припущення моделі про причину збою не прирівнюється до діагностики.

Публічний HTTPS перевіряється на кожному редиректі; DNS-адреса закріплюється під час встановлення TLS-з’єднання. Приватні адреси й HTTP downgrade блокуються. Ключ Brave не передається через редиректи. Для локального Bridge — явне закриття з’єднання та довжина JSON-відповіді; один повтор втраченої відповіді лише для READ_ONLY. Втрата результату зміни зберігає стан «невідомо».

Критерій: тести обриву після прийнятого POST, відсутності повтору зміни, повної помилки HTTP, редиректів/SSRF, порожнього пошуку, дублікатів, кешу й обмеження тексту. Окремо — реальний пошук на телефоні з Wi-Fi та мобільної мережі. Серверні перевірки не замінюють цей приймальний тест.

### P0 / етап 2. Контракт завершення задачі — план

Додати `GoalContract`, `AcceptanceCriterion`, `CriterionEvidence` до TaskState. Критерії мають стани pending/passed/failed/unknown і посилання на результат інструмента. Перша реалізація — перевірювані типові цілі: файл існує, файл відсутній, синтаксис перевірено, тести пройшли, процес відповідає, сторінку отримано. Чистий текст `print("deleted")` не доводить видалення.

Додати контрольований `file.remove` із підтвердженням і перевіркою лише явно вказаного шляху в workspace. Для самотесту вести список саме створених ним тимчасових об’єктів. Не генерувати нескінченні cleanup.py → final_cleanup.py → last_step.py. Не видаляти сторонні файли за широким шаблоном.

Завершення `done` дозволене, коли всі обов’язкові критерії виконані; інакше `partial` з точним переліком залишку. Довільні бізнес-цілі залишаються непідтвердженими без узгодженого способу оцінювання.

Критерій: самотест зі скриншотів завершується без ланцюжка cleanup-скриптів; вичерпання бюджету зберігає вже зроблене та залишає чесний частковий результат. Залежність: етап 1.

### P0 / етап 3. Єдиний контролер ресурсів — план

Додати `ResourceSnapshot`, `ModelCapabilities`, `ExecutionBudget` і `ResourceGovernor`. Кожне значення має джерело та тип: measured / estimated / unavailable. Поля: RAM пристрою й процесу, розмір ваг, контекстна місткість, фактичні/оцінені вхідні токени, резерв відповіді, KV-cache за доступними метриками, час кроку, кількість викликів, температура/тиск пам’яті за доступними Android API.

Окремі адаптери: embedded llama.cpp, Ollama, хмарний провайдер. Для хмари не показувати вигадану RAM сервера; враховувати опубліковані ліміти, usage відповіді та локально заданий бюджет вартості. Для llama.cpp використовувати власний токенізатор перед запитом; для іншої моделі без токенізатора показувати оцінку з запасом.

Політика: одна генерація на телефоні; резерв відповіді та перевірки; зменшення retrieved-контексту перед зменшенням обов’язкових правил; контрольований перехід на менший контекст/batch за виміряним тиском. Неможливе завантаження моделі закінчується діагностикою, а не циклом повторів.

UI-гармошка «Ресурси»: короткий стан, використано/залишилось, останнє рішення контролера, ручні межі в деталях. Критерій: ін’єкція low-memory / timeout / відсутніх метрик не породжує вигаданих чисел, повторних завантажень або втрати checkpoint. Залежність: етап 2.

### P1 / етап 4. Контекстна ОС з адресованою пам’яттю — план

Розділити незмінні правила, активну мету, робочу пам’ять, журнал доказів і довгостроковий досвід. Додати читання доказу за ID: капсула зберігає не весь текст, а перевірювані посилання, актуальність і стислий зміст. Запис не може називатися фактом без походження та часу отримання.

Збереження версії workspace/файлу дозволить інвалідувати застарілу перевірку після зміни. Стискання повинно зберігати мету, заборони, незавершену операцію, критерії, останні помилки й потрібні ID. Не стирати їх заради довгої історії розмови.

Перший пошук у пам’яті — SQLite FTS і лексична релевантність; embeddings додавати лише після вимірювання вигоди на телефоні. Критерій: після рестарту можна знайти доказ за ID, продовжити з незавершеного критерію та відрізнити актуальні результати від історичних. Залежність: 2–3.

### P1 / етап 5. Початкова конституція програмування й проєктів — план

Додати версійовані типізовані `Procedure` з передумовами, діями, очікуваними результатами, перевіркою, бюджетом та способом відновлення. Ідентифікатор рецепта супроводжується коротким поясненням, щоб слабка модель розуміла його без навчання нового алфавіту.

Початкові рецепти:

1. Діагностика: відтворити → зібрати помилку → перевірити причину → мінімально виправити → підтвердити результат.
2. Зміна коду: прочитати пов’язаний код/обмеження → зберегти користувацькі зміни → виправити причину → перевірити змінений об’єкт і пов’язану поведінку.
3. Проєкт: узгоджена мета й критерії → мінімальна вертикальна реалізація → перевірка → інструкція запуску → наступна ітерація.
4. Git: перевірити branch/status/diff → включити лише відповідні файли → перевірити commit → не ототожнювати commit, push, CI й deployment.
5. Дослідження: конкретне питання → пошук → першоджерела → зіставлення → цитовані висновки з невизначеністю.
6. Відновлення: класифікувати збій → перевірити фактичний стан → обмежений повтор/інший шлях → частковий звіт із наступною дією.

Глобальні правила: не вигадувати залежності, API, шляхи, результати тестів; секрети не записувати в журнали; не розширювати повноваження; не переписувати зайве; не називати систему стабільною за однією успішною командою. Рецепти не є довільним кодом, який модель може самостійно встановлювати.

Критерій: кожен рецепт має позитивний сценарій, контрприклад і тест зупинки; він доступний лише за потрібних передумов. Залежність: 2–4.

### P1 / етап 6. Ландшафт користі, а не частоти — план

Зберігати окремо `toolOutcome`, `goalOutcome`, якість перевірки, витрати часу/токенів, число втручань користувача та походження оцінки. Не зводити їх одразу в одну «розумність». Успіх інструмента не піднімає оцінку завершення всього завдання.

Вершини — перевірені ефективні процедури за відповідних умов. Ями — відтворювані невдачі з причинами та шляхом відновлення. Частота збільшує впевненість лише за різноманітних перевірених задач; вона не замінює якість. Ребра означають спостережувані переходи, а не доведену причинність.

Різні моделі/пристрої/версії середовища не отримують однакові ваги автоматично. Старіння, суперечності, зміна залежностей і версій знижують довіру. Оцінка користувача зберігається окремо від автоматичного тесту.

Критерій: сто повторів однієї успішної дрібниці не переважають незалежні провали мети; зміна моделі чи середовища не переносить довіру без перевірки. Залежність: 2, 5.

### P2 / етап 7. Контрольована еволюція конституції — план

Життєвий цикл: спостереження → кандидат → перевірка на відкладених задачах → тіньовий режим → обмежене застосування → прийняття/відкат. Лише типізовані шаблони з доказами. Текст вебсторінки, stderr чи відповіді моделі не може сам стати системною інструкцією.

Кожна зміна правила має версію, область застосування, джерела доказів, метрики до/після та причину. Регресія вимикає правило. Повноваження й сталі перевірки не саморедагуються. Розширення на інший домен чи модель спершу є експериментом.

Критерій: отруєний документ не змінює правила; відкат відновлює попередню поведінку; успіх на тренувальних випадках без покращення відкладених задач не активує правило. Залежність: 5–6.

### P2 / етап 8. Адаптація до слабких моделей і вимірювання — план

Зробити відтворюваний набір щонайменше 30 різних задач: файли, діагностика, самотест, код, пошук, відсутній інтернет, переповнення контексту, перезапуск, невідомий результат зміни. Для кожної — незалежний критерій результату. Закріпити версії моделей, seed/параметри генерації, пристрій та мережеві умови; зовнішні дані тестувати також на зафіксованих відповідях.

Порівняти: базовий агент; ядро; ядро+рецепти; ядро+рецепти+досвід. Виміряти завершення, помилковий done, цикли, токени, p50/p95 часу, пікову RAM і ручні втручання. Економію від «ДНК» приймати тільки коли менше токенів/часу при не гіршій якості й межах безпеки.

Критерій: спочатку отримати baseline; поріг прийняття встановити до експерименту. Автоматично не активувати нову версію при регресії невідомих змін, false-done або ресурсних збоїв. Не обіцяти універсальний відсоток покращення без вимірювання. Залежність: 1–7; baseline можна збирати паралельно з етапом 2.

## 5. Послідовність поставки

Перед подальшими оновленнями: закріпити підпис і визначити збереження стану вже встановленої версії.

1. Build 22: пошук, мережеве відновлення, правило джерел, цей план.
2. Наступний пакет: контракт завершення + самотест без cleanup-циклів.
3. Далі: вимірювані бюджети ресурсів + гармошка стану + адресована пам’ять.
4. Потім: доменні рецепти + оцінка результату всієї задачі.
5. Після baseline: еволюція правил з перевіркою на відкладених задачах.

Це послідовність залежностей, не обіцянка строків. Кожен пакет проходить CI та приймальний тест на телефоні. Паралельні агенти й рекурсивний планувальник не є передумовою: спершу потрібне надійне виконання одним агентом.

## 6. Приймальний сценарій для пошуку

Запит: «Знайди в інтернеті три актуальні інструменти для …; перевір офіційні сторінки, дай посилання й обмеження». Очікуємо web.search, потім web.read/http.json; факти прив’язані до джерел. При втраті інтернету — обмежене відновлення або partial, без вигаданих актуальних рекомендацій. Популярність, виручка і прибутковість — різні твердження, для кожного потрібні окремі докази.

Деталі провайдерів та налаштування: [web-search.md](web-search.md). Архітектура вже наявного ядра: [context-kernel.md](context-kernel.md), [experience-landscape.md](experience-landscape.md).
